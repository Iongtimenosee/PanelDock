# 文档与注释规范

**这份文件管的是「文档本身怎么长」。** 写文档或注释之前读它，改完对照末尾的清单自检。

## 一、文档分层

只有 5 份文档，**不要再新增第 6 份**。新内容先问归哪一层，放不进就说明现有某份该改。

| 文件 | 读者 | 回答什么问题 | 硬上限 |
|---|---|---|---|
| `AGENTS.md`（根） | 接手代码的人 / AI | 「改代码前必须先知道什么」 | 150 行 |
| `docs/architecture.md` | 同上 | 「现在是怎么做的 / 机制」 | 200 行 |
| `docs/behavior.md` | 同上 + 写 README 时 | 「用户可见行为的契约」 | 150 行 |
| `docs/pitfalls.md` | 同上 | 「哪一步会静默失败、为什么」 | 250 行 |
| `docs/doc-policy.md` | 同上 | 「文档与注释怎么写」 | 120 行 |
| `README.md` / `README.zh-CN.md` | **最终用户** | 「这是什么 / 怎么装 / 隐私」 | 各 130 行 |

**分层判据（唯一）**：一条内容只进一层，判据是「它回答上面哪个问题」。

- 说明**现在的行为** → `behavior.md`
- 说明**为什么会失败 / 反直觉** → `pitfalls.md`
- 说明**机制与流程** → `architecture.md`
- 三份都要写同一件事 = 分层错了，**结论留 behavior，坑留 pitfalls，机制留 architecture，其余删**。

## 二、写作规范

1. **结论先行**：第一句就是答案。不写「我们可以考虑…」「需要注意的是…」。
2. **不写过程、不写历史**：不记「某天改成 X」「之前试过 Y」。历史归 `git log`。
3. **不复制代码**：贴函数名 / 常量名 / 消息号就够，代码块会立刻过期。
4. **每条只说一件事**：一段超过 5 行就拆。用表格承载并列项。
5. **禁止自我表扬与营销腔**：技术文档里不写「优雅」「显然」「非常好」。
6. **中文为主**，技术标识符（API 名、字段、消息）保留原文。术语首次出现给全称。
7. **禁止「待补充 / TODO / 以后再说」占位**。没写完就别提交。
8. 加粗只给**不变量与禁令**，一屏最多 3 处。
9. **引用而非转述**：跨文件指向用 `文件#小节`（如 `docs/architecture.md#进程寿命`），不要重写一遍。

## 三、演进规则

| 改了什么 | 必须同步 |
|---|---|
| 用户可见行为（功能、交互、文案语义） | `behavior.md` + **两份 README** |
| 窗口生命周期 / 配置 / 设置项 / 数据路径 | `architecture.md` |
| 踩到新坑、或某条坑已不成立 | `pitfalls.md`（不成立的**直接删**，不留「曾经」） |
| 新增 / 删除源文件、职责变更 | `AGENTS.md` 的文件地图 |
| 新增桥接方法 | `AGENTS.md` 文件地图 + 手工补 `App.js`（见 pitfalls#Wails 集成） |

**每次改行为问一句：README 里那句话还成立吗？** 两份 README 是逐节对应的翻译，改一处就要改两处。

## 四、防膨胀机制

`docs_test.go`（纳入 `go test ./...`；`go test -run TestDocs .` 单独跑）自动守四条：

1. **行数上限**（见上表）超出即失败。想超？先压缩现有内容，不是改上限。
2. **中英 README 结构一致**：两文件的标题序列必须逐条相同（防翻译漂移）。
3. **文档引用有效**：`AGENTS.md` 里提到的 `docs/*.md` 必须真实存在；文档里不得留占位标记。
4. **注释占比**：≥200 行的源文件，注释行不得超过 25%。超了说明注释在替文档干活，删掉复述部分。

这四条失败时的错误信息都指向本文件 —— 别去看测试代码，先读这里的规则。

## 五、注释规范

### 写什么

**只写「为什么」，不写「做了什么」。** 代码能自解释的部分不加注释。

必写：

- **反直觉的取舍**（为什么不用更简单的写法）
- **静默失败的前提**（「返回 S_OK 不代表生效」「必须按值传」）
- **顺序依赖 / 时序约束**（「必须在 navigate 之前」「先关窗口再清」）
- **不变量的落点**（「四个地方都要改」）
- **非显然的常量语义**（魔数、位标志、槽位号）

不写：

- 复述函数名 / 语句字面意思
- **复述本文档里已有的规则** —— 写指针：`// 见 docs/architecture.md#进程寿命`
- 变更历史、作者、日期（归 git）
- 注释掉的代码块（直接删）
- 对未来的承诺（「以后可以…」）

### 放在哪

| 位置 | 写什么 |
|---|---|
| 文件顶部 | 该文件的**职责边界**：管什么、**不管什么**（边界比职责更重要） |
| 类型 / 结构体 | 它的生命周期与不变量，不是字段罗列 |
| 导出函数 | 契约：前置条件、副作用、返回值语义 |
| 非导出函数 | 只在「为什么这么写」不明显时写，一句话 |
| 常量 / 枚举 | 非显然的取值语义；取值显而易见的（如颜色）不写 |
| 行内 | 只用于「下一行看着像 bug 但其实是对的」 |

### 硬性限制

- 单文件注释行占比 **≤ 20%**（注释 > 代码的文件 = 代码该拆了，不是注释该加）。
- 单个注释块 **≤ 4 行**。超过就说明该进 `docs/`，代码里留指针。
- 注释与代码之间不留空行分隔（空行会让注释与对象脱钩）。

### 风格

- 中文，句末不加句号（列表项）或加句号（段落），同一块内统一。
- 开头写被注释对象的名字是 Go 惯例（`// newPanelWindow 创建…`），保留。
- 禁令用**不要**而不是「建议避免」。

### 与文档的分工

```
代码注释  → 这个函数为什么这么写（局部、贴身、随代码移动）
docs/     → 这套系统的规则是什么（全局、跨文件、需要索引）
```

同一条规则在两边都出现 = 注释里留指针，正文只留一份。
